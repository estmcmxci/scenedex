# Strategy: types.ts as Architectural Foundation

---

## **1. Understanding the Dependency Graph**

```
                        types.ts (THE HUB)
                            ▲
            ┌───────────────┼───────────────┐
            │               │               │
            ▼               ▼               ▼
     validation.ts      store.ts      components/
          ▲               ▲ ▼            (all use)
          │               ▼ │
          │          mocks/fixtures.ts
          │               ▲
          └───────────────┘
                ▲
                │
            lib/utils/
            ipfs.ts (build IPFS metadata from Release)
```

**Key principle**: Every downstream file imports from types.ts. Nothing defines its own data shape.

## **2. Structure of types.ts (4 Sections)**

### **Section A: Input Types (User-provided data)**

```typescript
// What users submit via form
export type ReleaseSubmissionInput = {
  title: string;
  description: string;
  media: string; // IPFS CID the user already uploaded
  // Optional metadata
  artists?: string;
  duration?: number;
  format?: string;
};
```

**Why this exists**: Form validation outputs this type. Store receives this.

---

### **Section B: Core Release Type (All states)**

```typescript
// The complete Release object at any state
export type Release = {
  // Immutable
  id: string;                      // PDA-XXX (generated by system)
  createdBy: string;               // 0xWallet
  createdAt: number;               // timestamp
  
  // From submission
  title: string;
  description: string;
  media: string;                   // ipfs://Qm...
  
  // Lifecycle state
  status: 'pending' | 'approved' | 'published';
  
  // After curator approval
  approvedBy?: string;             // 0xCuratorWallet
  approvedAt?: number;             // timestamp
  rejectionReason?: string;        // if rejected
  
  // After IPFS metadata creation
  metadataURI?: string;            // ipfs://QmMetadata
  
  // After Zora mint (Base L2)
  zoraNFT?: string;                // base:0xZoraAddress/tokenId
  tokenId?: string;                // numeric string from Zora
  
  // After ENS registration (L1)
  ensSubname?: string;             // e.g., "first-release.palaupalau.eth"
};
```

**Why this structure**:
- All fields in one type = single source of truth
- Optional fields (`?`) reflect state transitions
- A `pending` release won't have `zoraNFT`
- A `published` release will have all fields

---

### **Section C: Refined State Types (Type Guards)**

```typescript
// These ensure type safety at each state
export type PendingRelease = Release & {
  status: 'pending';
  // No approval fields required yet
};

export type ApprovedRelease = Release & {
  status: 'approved';
  approvedBy: string;       // Required
  approvedAt: number;       // Required
};

export type PublishedRelease = Release & {
  status: 'published';
  metadataURI: string;      // Required
  zoraNFT: string;          // Required
  tokenId: string;          // Required
  approvedBy: string;       // Required
  approvedAt: number;       // Required
};
```

**Why this exists**: Component can be type-safe about state:
```typescript
function DisplayNFT({ release }: { release: PublishedRelease }) {
  // TypeScript KNOWS release.zoraNFT exists
  return <div>{release.zoraNFT}</div>;
}
```

---

### **Section D: IPFS Metadata Type (ERC721 + Custom)**

```typescript
// What gets uploaded to IPFS
// Must be compatible with ERC721 + Zora extensions
export type IPFSMetadata = {
  // ERC721 Standard (required by Zora)
  name: string;
  description: string;
  image: string;                    // IPFS URI to cover art
  
  // Zora extensions
  animation_url?: string;           // IPFS URI to audio/video
  content?: {
    mime: string;                   // "audio/mpeg", "video/mp4", etc
    uri: string;                    // IPFS URI to media file
  };
  
  // Optional ERC721 fields
  external_url?: string;            // Link back to catalogue
  attributes?: Array<{
    trait_type: string;
    value: string | number;
  }>;
  
  // Custom catalogue fields (stored in properties)
  properties: {
    // Back-reference to catalogue
    catalogueId: string;            // PDA-001
    catalogueVersion: number;       // 1 (for future upgrades)
    catalogueUrl: string;           // https://catalogue.palaupalau.eth/release/PDA-001
    
    // Provenance
    submittedBy: string;            // 0xCreatorWallet
    submittedAt: number;            // timestamp
    approvedBy: string;             // 0xCuratorWallet
    approvedAt: number;             // timestamp
    
    // Music-specific metadata
    category: string;               // "music"
    format?: string;                // "mp3", "wav", "flac"
    duration?: number;              // seconds
    artists?: string;               // "Artist Name"
    genre?: string;                 // "Electronic"
  };
};
```

**Why split into Release + IPFSMetadata**:
- `Release` = internal catalogue representation
- `IPFSMetadata` = what goes on immutable storage
- They're different shapes because they serve different purposes

---

### **Section E: Action Types (Curator & Fallback)**

```typescript
// What a curator does
export type CuratorAction = {
  releaseId: string;
  action: 'approve' | 'reject';
  reason?: string;                  // if reject
};

// Result of fallback resolution attempt
export type ResolutionResult = {
  source: 'catalogue' | 'ens' | 'ipfs' | 'zora';
  release: Release;
  fallbackUsed: boolean;
};
```

**Why this exists**: Store methods accept these types as parameters.

## **3. How types.ts Flows Into Each Downstream File**

### **Flow 1: types.ts → validation.ts**

```
lib/types.ts
    ↓
    ├─ export type ReleaseSubmissionInput
    │
lib/validation.ts
    ├─ import { ReleaseSubmissionInput } from '@/lib/types'
    ├─ const ReleaseSubmissionSchema = z.object({
    │     title: z.string().min(1),
    │     description: z.string().min(10),
    │     media: z.string().regex(/^ipfs:\/\//),
    │     artists: z.string().optional(),
    │   });
    │
    └─ export type ReleaseSubmissionInput = z.infer<typeof ReleaseSubmissionSchema>
       (This MUST match types.ts version)

components/MetadataForm.tsx
    ├─ import { ReleaseSubmissionInput } from '@/lib/types'
    ├─ import { ReleaseSubmissionSchema } from '@/lib/validation'
    ├─ const { register } = useForm<ReleaseSubmissionInput>({
    │     resolver: zodResolver(ReleaseSubmissionSchema)
    │   });
    └─ onSubmit receives typed data: ReleaseSubmissionInput
```

**Why this chain**:
1. types.ts defines the shape
2. validation.ts adds validation rules + type guard
3. Components use validated type + schema for form binding

---

### **Flow 2: types.ts → store.ts → components**

```
lib/types.ts
    ├─ export type Release
    ├─ export type PublishedRelease
    │
lib/store.ts
    ├─ import { Release, PublishedRelease, ReleaseSubmissionInput } from '@/lib/types'

    │     allReleases: PublishedRelease[];

```

**Why this chain**:
1. types.ts defines what Release looks like
2. store.ts uses typed methods that return/accept Release
3. Components receive typed props from store

### **Flow 4: types.ts → lib/utils/ipfs.ts**

```
lib/types.ts
    ├─ export type Release
    ├─ export type IPFSMetadata
    │
lib/utils/ipfs.ts
    ├─ import { Release, IPFSMetadata } from '@/lib/types'
    ├─ export function releaseToIPFSMetadata(release: Release): IPFSMetadata {
    │     // TypeScript enforces the mapping
    │     return {
    │       name: release.title,                // string → string ✅
    │       description: release.description,
    │       image: release.media,               // wait, media is audio not image ✅
    │       animation_url: release.media,       // ← compiler catches this
    │       content: {
    │         mime: 'audio/mpeg',
    │         uri: release.media,
    │       },
    │       properties: {
    │         catalogueId: release.id,
    │         submittedAt: release.createdAt,
    │         approvedBy: release.approvedBy,   // ← must be defined
    │         approvedAt: release.approvedAt,   // ← must be defined
    │       },
    │     };
    │   }
```

**Why this matters**:
1. The function signature `(release: Release) → IPFSMetadata` documents the transformation
2. If Release type changes, function breaks and you see it immediately
3. No guessing about field names or types

## **4. The Cascading Safety Pattern**

### **Example: Detecting a Bug**

**Scenario**: Someone wants to add a new field to Release.

```typescript
// Step 1: Update types.ts
export type Release = {
  // ...existing fields...
  royaltyPercentage?: number;  // ← new field
};

// Step 2: TypeScript compiler breaks everything downstream
components/ReleaseCard.tsx         ← ❌ New optional field should be handled
lib/mocks/fixtures.ts             ← ❌ Mocks missing the field
lib/utils/ipfs.ts                 ← ❌ Mapping doesn't convert it
app/api/submit/route.ts           ← ❌ API handler doesn't return it

// Step 3: Developer fixes each one
// Now the new field is consistently added everywhere

// Step 4: Deploy with confidence
// No accidental omissions across the codebase
```

**Without types.ts**:
```typescript
// Someone adds royaltyPercentage to fixtures
export const MOCK_RELEASES = [{
  royaltyPercentage: 5,  // ← only here
}];

// But forgot to add to store
interface CatalogueStore {
  releases: {
    id: string;
    title: string;
    // Missing royaltyPercentage
  }[];
}

// Component tries to access it
<span>{release.royaltyPercentage}</span>  // ← undefined at runtime ❌

// Hard to debug: "why is it undefined here but works in that component?"
```

## **5. Execution Strategy: The 4-Phase Rollout**

### **Phase 1: Define Core Types (30 min)**

Create `lib/types.ts` with sections A-E (shown above).

**Deliverable**: Single file, 150-200 lines, no dependencies.

```typescript
// lib/types.ts - COMPLETE, FINAL
export type ReleaseSubmissionInput = {...};
export type Release = {...};
export type PendingRelease = {...};
export type ApprovedRelease = {...};
export type PublishedRelease = {...};
export type IPFSMetadata = {...};
export type CuratorAction = {...};
```

**Checkpoint**: TypeScript should have zero errors (even if unused).

---

### **Phase 2: Validation Layer (45 min)**

Create `lib/validation.ts` that uses the types from Phase 1.

**Rule**: Every type from types.ts gets a Zod schema.

```typescript
// lib/validation.ts
import { ReleaseSubmissionInput, Release, IPFSMetadata } from '@/lib/types';

export const ReleaseSubmissionSchema = z.object({...});
export const ReleaseSchema = z.object({...});
export const IPFSMetadataSchema = z.object({...});

// Re-export for type inference
export type ReleaseSubmissionInput = z.infer<typeof ReleaseSubmissionSchema>;
```

**Checkpoint**: Validation types match types.ts exactly.

---

### **Phase 3: State Management (1-2 hours)**

Create `lib/store.ts` that:
- Imports types from Phase 1
- Uses schemas from Phase 2
- Defines store interface with methods that accept/return typed data

```typescript
// lib/store.ts
import { Release, PublishedRelease, ReleaseSubmissionInput, CuratorAction } from '@/lib/types';
import { ReleaseSubmissionSchema } from '@/lib/validation';

interface CatalogueStore {
  submissions: Release[];
  allReleases: PublishedRelease[];
  
  submitRelease: (input: ReleaseSubmissionInput) => Promise<Release>;
  approveRelease: (id: string) => Promise<PublishedRelease>;
}

export const useCatalogueStore = create<CatalogueStore>((set) => ({
  // Implementation here
}));
```

**Checkpoint**: Store methods have clear input/output types.

---

### **Phase 4: Mocks & Components (2-3 hours)**

Create:
- `lib/mocks/fixtures.ts` (typed mocks)
- `lib/mocks/handlers.ts` (MSW handlers with types)
- `components/*.tsx` (components using types)

```typescript
// lib/mocks/fixtures.ts
import { PublishedRelease } from '@/lib/types';

  // TypeScript enforces all fields

```

**Checkpoint**: All components compile without errors.

## **6. The Key Principle: Unidirectional Dependency**

```
types.ts (imports nothing)
  ↓
  ├─ validation.ts (imports types.ts)
  │   ↓
  │   ├─ lib/store.ts (imports types.ts + validation.ts)
  │   ├─ components/ (imports types.ts + validation.ts)
  │   └─ lib/utils/ (imports types.ts)
  │
  ├─ lib/mocks/ (imports types.ts)
  │
  └─ app/api/ (imports types.ts) [Phase 3]
```

**Rule**: 
- ✅ types.ts can stand alone
- ✅ validation.ts can import types.ts
- ✅ store.ts can import types.ts + validation.ts
- ❌ types.ts should NEVER import from store.ts, validation.ts, or components

This prevents circular dependencies and keeps types as the stable foundation.

## **7. Why This Order Matters**

### **If you do it RIGHT (types first):**

```
Step 1: Define types.ts
  ↓ (compiler helps catch problems)
Step 2: Write validation
  ↓ (types enforced)
Step 3: Build store
  ↓ (store methods are typed)
Step 4: Create components
  ↓ (components get typed props from store)
Step 5: Add mocks
  ✅ Everything uses same type definitions
```

**Result**: Consistent data flow, easy refactoring, clear contracts.

### **If you skip types (common mistake):**

```
Step 1: Write store (any types)
  ↓
Step 2: Write components (unknown shape)
  ↓
Step 3: Write validation (maybe matches store?)
  ↓
Step 4: Write mocks (maybe matches components?)
  ✅ or ❌ ???

Result: Constant "this field doesn't exist" bugs
```

## **8. Practical Benefit: Refactoring is Safe**

**Example**: You realize `description` should be 5000 chars, not 2000.

```typescript
// Step 1: Update types.ts
export type ReleaseSubmissionInput = {
  description: string;  // No change needed here (description is description)
};

// Step 2: TypeScript finds everywhere that validates description
lib/validation.ts:
  ❌ Max length 2000, now needs 5000

// Step 3: Update validation
export const ReleaseSubmissionSchema = z.object({
  description: z.string()
    .min(10, 'Minimum 10 chars')
    .max(5000, 'Maximum 5000 chars'),  // ← changed
});

// Step 4: Run tests, everything passes
// No surprises at runtime

// Result: 5-minute change, 100% confidence
```

**Without types**:
```
❌ Guess where description is validated
❌ Hope no component has hardcoded length check
❌ Mocks might not reflect new length
❌ Deploy and hope for best
```
