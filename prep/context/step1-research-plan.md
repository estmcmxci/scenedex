## Phase 1A: Research & Constraint Discovery

### A1: ENS Subname Metadata Requirements (L1)
**Goal:** Understand how ENS subnames store and resolve metadata

**Key Questions:**
- How do ENS resolver contracts store arbitrary metadata? (e.g., `text` records, `contenthash`)
- What is the maximum size/format for metadata in ENS records?
- Can we store a link to IPFS metadata via ENS resolver?
- What resolver contract standard should we target? (PublicResolver, Custom Resolver)
- Can we store a Zora NFT reference (chain:contract/tokenId) in ENS metadata?

**Research Tasks:**
1. Read ENS resolver specification (PublicResolver)
2. Check if ENS `text` records support arbitrary key-value pairs
3. Determine if we can store URLs/URIs in ENS records
4. Look for examples of projects storing NFT metadata via ENS

**Output:** `research/ens-spec.md` - Contains resolver capabilities and limits

---

### A2: Zora Creator Contract on Base (L2)
**Goal:** Understand the Zora Creator contract's token metadata expectations

**Key Questions:**
- What is the Zora Creator contract interface? (Does it follow ERC721Metadata?)
- What format does `tokenURI()` return? (JSON URL or inline?)
- Can we store arbitrary metadata in the JSON at `tokenURI`?
- What metadata fields does Zora require/expect/support?
- Can we reference external identifiers (palaupalau.eth, PDA-001) in Zora metadata?
- What chain is the contract on? (Base Mainnet / Base Sepolia)
- What deployment do we need? (Existing contract or deploy new one?)

**Research Tasks:**
1. Fetch Zora Creator contract ABI and specification
2. Review ERC721Metadata standard
3. Check Zora documentation for metadata requirements
4. Look at example Zora tokens and their metadata
5. Verify Base network details (RPC endpoints, deployment status)

**Output:** `research/zora-creator-spec.md` - Contains contract interface and metadata format

---

### A3: IPFS Metadata Standard (ERC721 Metadata URI JSON Schema)
**Goal:** Understand the standard format for NFT metadata on IPFS

**Key Questions:**
- What is the ERC721 Metadata JSON Schema standard?
- What fields are required vs optional?
- Can we add custom fields beyond the standard?
- What is the recommended file structure on IPFS?
- How do we reference media files (image, audio, etc.)?
- What content types are supported (audio, video, documents)?
- Should we include provenance/licensing metadata?

**Research Tasks:**
1. Read ERC721 Metadata URI spec
2. Review example IPFS metadata for music/media NFTs
3. Check music-specific metadata standards (if any)
4. Look at Zora's example metadata payloads
5. Research IPFS file structure best practices

**Output:** `research/ipfs-metadata-standard.md` - Contains ERC721 schema + media-specific extensions

### A4: Compatibility Analysis
**Goal:** Map out how all three systems interact and what metadata each needs

**Compatibility Matrix:**
```
┌─────────────────────────────────────────────────────────┐
│  Source System  │  Stores In       │  Reads What?        │
├─────────────────────────────────────────────────────────┤
│  ENS (L1)       │  Text Records    │  URL to IPFS? ID?   │
│  Zora (Base)    │  tokenURI JSON   │  Full Metadata      │
│  IPFS           │  JSON Blob       │  ERC721 Schema      │
│  Catalogue DB   │  Internal Store  │  Full Release obj   │
└─────────────────────────────────────────────────────────┘
```

**Mapping Example:**
```
User creates Release in Catalogue
  ↓
Stored in Catalogue (internal: Release)
  ↓
Curator approves
  ↓
Create IPFS metadata JSON (ERC721 + custom fields)
  ↓
Upload to IPFS → metadataURI = ipfs://Qm...
  ↓
Mint NFT on Zora contract on Base
  ↓ tokenURI points to metadataURI
  ↓
Register ENS subname pointing to Release
  ↓ text record: "catalogueId" = "PDA-001" or URL to Catalogue
  ↓
Fallback resolution: ENS → IPFS (via Zora) → Catalogue
```

**Output:** `research/compatibility-matrix.md` - Documents data flow and field mappings

## Phase 1B: Define the Data Model

### B1: Catalogue Release Model (Internal)
**File:** `lib/types.ts`

Based on research, the Release model should:
1. **Core fields** (user-provided during submission):
   - `title`: string (required)
   - `description`: string (required)
   - `media`: string (IPFS URI, required)
   - `additionalMetadata`: object (custom fields from user)

2. **System fields** (generated by catalogue):
   - `id`: string (PDA-XXX, generated)
   - `createdBy`: string (wallet address)
   - `createdAt`: number (timestamp)
   - `status`: 'pending' | 'approved' | 'published'

3. **L2 Fields** (populated after Zora mint):
   - `zoraNFT`: string (base:0xZoraAddress/tokenId)
   - `tokenId`: string (from Zora)
   - `metadataURI`: string (ipfs://QmXXX, uploaded to IPFS)

4. **L1 Fields** (populated after ENS registration):
   - `ensSubname`: string (e.g., "first-release.palaupalau.eth")
   - `ensResolver`: string (contract address)

5. **Governance fields**:
   - `approvedBy`: string (curator wallet)
   - `approvedAt`: number (timestamp)
   - `rejectionReason`: string (if rejected)

**Why this structure:**
- Separates user input (immutable) from system-generated (mutable)
- Tracks state at each layer (Catalogue → IPFS → Zora → ENS)
- Allows fallback resolution by storing minimal ENS data

### B2: IPFS Metadata JSON (ERC721 + Custom)
**File:** `lib/types.ts` (separate type)

```typescript
interface IPFSMetadata {
  // ERC721 Standard Fields
  name: string;
  description: string;
  image: string; // IPFS URI or URL
  
  // Optional ERC721 Fields
  external_url?: string;
  attributes?: Array<{ trait_type: string; value: string }>;
  
  // Music/Media Specific
  animation_url?: string; // IPFS URI to audio/video
  properties?: {
    creators?: Array<{ name: string; share: number }>;
    category?: string; // 'music' | 'video' | 'artwork' | etc
    duration_seconds?: number;
    bitrate?: string;
    format?: string; // 'mp3' | 'wav' | 'ogg' | etc
  };
  
  // Catalogue-Specific
  catalogueId: string; // PDA-XXX
  catalogueUrl: string; // https://palaupalau.eth/release/PDA-XXX
  catalogueMetadata: {
    submittedAt: number;
    submittedBy: string;
    approvedAt: number;
    approvedBy: string;
  };
}
```

**Why this structure:**
- Follows ERC721 standard for Zora compatibility
- Extends with media-specific fields for music releases
- Stores back-reference to Catalogue (enables fallback)
- Includes provenance/approver info
